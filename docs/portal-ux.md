# App Depot Portal UX architecture

The Portal is the browser administration interface for the existing Server and API. It is a developer console for arbitrary software artifacts, not an app store or runtime manager. App names, release state, and visibility lead everyday screens; UUIDs, hashes, and internal identities remain available as secondary technical details. No installer, platform, executable format, declaration, or channel is mandatory.

## Workspaces and navigation

The Server workspace has Overview and Applications. Server Admin areas are Users & Access, Backups, Diagnostics, and Server Settings; they appear only as their screens are implemented. Account actions belong in the top-right user menu. There is no global Operations navigation item because the API has no operation list. Known operations remain accessible from the action that started them.

Selecting an App changes the sidebar to Overview, Releases, Channels, Declarations, and Settings. The current App name and a route back to Applications remain visible. Artifacts belong within their Release context. A Published Release can still be Private because App visibility is separate from Release state. Channels are optional and have no mandatory names.

Stable route conventions are `/` and `/apps` for the Server, `/apps/:appId` for an App, and child routes under `/apps/:appId` for App work. Authentication uses `/login` and `/setup` outside the workspace shell. The App workspace implements `/apps/:appId/releases`, `/apps/:appId/releases/new`, `/apps/:appId/releases/:releaseId`, `/apps/:appId/channels`, `/apps/:appId/declarations`, and `/apps/:appId/settings`. Uploading to a new App, an existing App with an implicit Draft Release, or an existing Draft Release uses `/upload/new-app`, `/apps/:appId/uploads/new`, or `/apps/:appId/releases/:releaseId/uploads/new`, respectively. Reserved routes for later work are `/admin/users`, `/admin/backups`, `/admin/diagnostics`, `/admin/settings`, `/operations/:id`, and `/account`; the Portal does not advertise them as working pages.

Declarative React Router provides nested routes, browser history, and direct reloads. The existing Server static-file fallback serves the Portal entry point on those routes. Page data is fetched through the API rather than stored in a global client-side catalog.

## Visual and interaction rules

Use neutral surfaces, one blue accent, semantic success/danger/neutral statuses with text as well as color, system fonts, and a spacing scale of 4, 8, 12, 16, 24, 32, and 48 px. Light and dark themes share semantic CSS tokens. Initial theme follows the OS; a local preference is available from the interface without changing Server settings. Tables prioritize human names and states, with technical values disclosed on demand. Each page has one clear primary action. Empty, loading, error, and permission states describe the actual outcome and next available action.

The application shell owns workspace navigation, context, theme access, and account actions. Page headers, actions, status badges, empty/loading states, problem notices, confirmation dialogs, and technical details are reusable only where needed. A centralized API client handles same-origin cookies, CSRF, secure LAN-HTTP-compatible UUIDv4 idempotency keys, strong ETags, Problem Details, cancellation, and authorization errors. It does not replace Server authorization. An exact retry of a create or upload request retains its idempotency key while its inputs remain unchanged. Publication and visibility are distinct decisions; an upload or registration never silently publishes. Deletion shows access revocation and physical cleanup separately through the operation status.

The uploader supports BareFile, BareTree, and ZipImport without loading an entire large file into memory. It sends chunks, consults authoritative progress before resuming, freezes tree inventory before byte transfer, and uses server-assigned file IDs. When browser session storage is available, matching upload keys survive a reload of the same tab after the user selects the same inputs again; transfers do not continue in the background. In-tab retries remain available without browser storage. The browser directory picker may omit empty directories, so the form accepts explicit relative empty-directory paths. Browsers do not provide portable executable-bit metadata; tree files selected through this Portal are marked non-executable. A BareTree requires at least one regular file under the Server contract. ZIP import is validated by the Server.

The sidebar is persistent on desktop and a dismissible drawer below 900 px. Narrow forms use one column; tables retain readable primary fields and may scroll for technical data. Navigation, forms, and menus work with a keyboard, with visible focus and meaningful labels. Status changes use live text; reduced-motion preferences disable nonessential transitions.

## Current scope and future work

The Portal provides session restoration, setup/login/logout, Server Overview, application search with server cursors, Draft App creation without an artifact, App metadata/visibility edits, Release creation and details, Artifact association and inventory, File and Tree downloads, optional channels and movement history, and App/Release/association declaration revisions. Published Release composition is immutable, while declarations remain separately editable by authorized owners/Admins. Permanent deletion requires confirmation and reports asynchronous cleanup. Admin-only diagnostic aggregates may appear on Server Overview. The Portal does not infer release counts, activity feeds, storage history, per-App grants, or global operation lists from incomplete data. Server administration areas, account management, and contextual operation pages remain future work; new backend capabilities require separate authorization and contract updates.
