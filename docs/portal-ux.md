# App Depot Portal UX architecture

The Portal is the browser administration interface for the existing Server and API. It is a developer console for arbitrary software artifacts, not an app store or runtime manager. App names, release state, and visibility lead everyday screens; UUIDs, hashes, and internal identities remain available as secondary technical details. No installer, platform, executable format, declaration, or channel is mandatory.

## Workspaces and navigation

The Server workspace has Overview and Applications. Server Admin areas are Users & Access, Backups, Diagnostics, Import Sources, and Server Settings; they appear only to Server Admins. Account actions belong in the top-right user menu in either workspace. There is no global Operations navigation item because the API has no operation list. Known operations remain accessible from the action that started them and through a direct `/operations/:id` URL.

Selecting an App changes the sidebar to Overview, Releases, Artwork, Channels, Declarations, and Settings. The current App name and a route back to Applications remain visible. Artifacts belong within their Release context. A Published Release can still be Private because App visibility is separate from Release state. Channels are optional and have no mandatory names.

Stable route conventions are `/` and `/apps` for the Server, `/apps/:appId` for an App, and child routes under `/apps/:appId` for App work. Authentication uses `/login` and `/setup` outside the workspace shell. The App workspace implements `/apps/:appId/releases`, `/apps/:appId/releases/new`, `/apps/:appId/releases/:releaseId`, `/apps/:appId/releases/:releaseId/artifacts/:associationId` for the Explorer, `/apps/:appId/artwork`, `/apps/:appId/channels`, `/apps/:appId/declarations`, and `/apps/:appId/settings`. Adding an Artifact to a new App, an existing App with an implicit Draft Release, or an existing Draft Release uses `/artifacts/new-app`, `/apps/:appId/artifacts/new`, or `/apps/:appId/releases/:releaseId/artifacts/new`, respectively. Previous `/upload/...` and `/import/...` routes remain usable bookmarks and open the same workflow with the corresponding source selected; source and type choices are reflected in URL query parameters. Server administration uses `/admin/users`, `/admin/backups`, `/admin/diagnostics`, `/admin/import-sources`, and `/admin/settings`. Account and known-operation routes are `/account` and `/operations/:id`.

Declarative React Router provides nested routes, browser history, and direct reloads. The existing Server static-file fallback serves the Portal entry point on those routes. Page data is fetched through the API rather than stored in a global client-side catalog.

## Visual and interaction rules

Add Artifact uses one source selector (Upload from this device or Import from server storage) and one independent Artifact type selector (Single file, Directory tree, ZIP import or GOG Offline Installer from Server Storage). Single file preserves ZIP bytes as an opaque File Artifact; ZIP import explicitly extracts a Tree Artifact. The selected source owns its file or authorized-root browser, transfer and progress logic. Changing source or type during active work is disabled; navigation away stops the browser stream while Server state remains authoritative for retry. The server browser lists only roots authorized for the current user and regular files or directories beneath them; host paths and symlink targets are never shown. Inbox is the initial Server source when available. Admin Import Sources shows Inbox availability, configured roots and their container paths without offering host filesystem controls. Device upload shows hashing and acknowledged transfer progress; Server import shows scanning, transfer, verification, ZIP extraction and CAS registration with indeterminate phases when no measured fraction exists. Terminal states distinguish registration from optional publication. Original Server sources remain untouched, and registered CAS content remains after source removal. An exact retry retains its key and rechecks source claims; the Server's original-byte verification remains authoritative.

Use neutral surfaces, one blue accent, semantic success/danger/neutral statuses with text as well as color, system fonts, and a spacing scale of 4, 8, 12, 16, 24, 32, and 48 px. Light and dark themes share semantic CSS tokens. Initial theme follows the OS; a local preference is available from the interface without changing Server settings. Tables prioritize human names and states, with technical values disclosed on demand. Each page has one clear primary action. Empty, loading, error, and permission states describe the actual outcome and next available action.

The application shell owns workspace navigation, context, theme access, account actions and a small persistent Server version indicator. It reads embedded build version and revision from public capabilities; local or unavailable metadata has a neutral label. Page headers, actions, status badges, empty/loading states, problem notices, confirmation dialogs, and technical details are reusable only where needed. A centralized API client handles same-origin cookies, CSRF, secure LAN-HTTP-compatible UUIDv4 idempotency keys, strong ETags, Problem Details, cancellation, and authorization errors. It does not replace Server authorization. An exact retry of a create or upload request retains its idempotency key while its inputs remain unchanged. Publication and visibility are distinct decisions; an upload or registration never silently publishes. Deletion shows access revocation and physical cleanup separately through the operation status. Active operations are polled for a bounded period and stop on unmount or terminal status.

The uploader supports BareFile, BareTree, and ZipImport without loading an entire large file into memory. It sends chunks, consults authoritative progress before resuming, freezes tree inventory before byte transfer, and uses server-assigned file IDs. When browser session storage is available, matching upload keys survive a reload of the same tab after the user selects the same inputs again; transfers do not continue in the background. In-tab retries remain available without browser storage. The browser directory picker may omit empty directories, so the form accepts explicit relative empty-directory paths. Browsers do not provide portable executable-bit metadata; tree files selected through this Portal are marked non-executable. A BareTree requires at least one regular file under the Server contract. ZIP import is validated by the Server.

BareTree selection excludes only common macOS and Windows metadata by default: `.DS_Store`, AppleDouble `._*`, content under `.Spotlight-V100`, `.Trashes` or `.fseventsd`, and case-insensitive `Thumbs.db`, `ehthumbs.db` and `desktop.ini`. The preparation summary counts excluded files; the user can disable the option for an exact upload. Other hidden files remain ordinary content. Exclusion applies before hashing, inventory registration and transfer, including explicit metadata directory paths, and its setting is part of the resumable upload identity. The Portal never changes source files. File size and modification time are checked between hashing and transfer when the browser exposes updated metadata; browser `File` metadata may be a snapshot and directory modification times are unavailable through this picker, so a second SHA-256 pass over the exact transferred buffers provides the stronger file-content change check before finalization.

The upload view reports file and byte progress while hashing, inventory registration and transfer. Transfer percentage counts Server-acknowledged bytes; it never denotes a committed Artifact. Verification, CAS commit and explicit publication remain separate phases with indeterminate progress when the Server provides no measured fraction. The browser hashes the exact bounded byte buffers it transfers and checks them against its earlier source hash before finalization; a changed source requires reselecting the files and a new upload. A terminal Server mismatch reports the failing logical file to the authorized user. Interrupted transfers may resume only from authoritative Server ranges with the same bound idempotency keys.

The sidebar is persistent on desktop and a dismissible drawer below 900 px. Narrow forms use one column; tables retain readable primary fields and may scroll for technical data. Navigation, forms, and menus work with a keyboard, with visible focus and meaningful labels. Status changes use live text; reduced-motion preferences disable nonessential transitions.

## Current scope and API limits

The Portal provides session restoration, setup/login/logout, Server Overview, application search with server cursors, Draft App creation without an artifact, App metadata/visibility edits, Release creation and details, Artifact association and inventory, File and Tree downloads, optional channels and movement history, and App/Release/association declaration revisions. Published Release composition is immutable, while declarations remain separately editable by authorized owners/Admins. Permanent App and Release deletion requires confirmation and reports asynchronous cleanup. Admin-only diagnostic aggregates may appear on Server Overview.

App, Release and association declarations open in standard-field mode when their current JSON structure supports it; otherwise they open in Advanced JSON without rewriting the value. Switching modes keeps unsaved form contents mounted until the next saved revision. The forms validate only the fields they edit in the `appDepot` object, preserve other JSON properties, and save a whole-document revision with a strong ETag. App fields cover optional summary, description, free-form kind (with suggestions), developer, publisher, homepage URL, license, tags and categories; identity and visibility remain separate. App Overview summarizes current standard metadata and links to editing. Release Details places optional notes, multiple platform presets or custom strings, and runtime metadata near its version. Advanced JSON retains support for any JSON value, including `null`, and revision inspection and restoration. A Release's Contents / Artifacts section prominently links to the Explorer for each association and directly when there is only one Artifact. The Explorer provides tree breadcrumbs, original paths, paginated directory listing, path search, file metadata and downloads, or a single-file detail view. Owners/Admins can select regular files as optional entry points, add multiple points, edit labels and platform constraints, change targets, remove points, and optionally declare `NativePortableV1` with a working directory and literal arguments. This setting never appears automatically on legacy points and never follows from a file name or executable flag. The Server reports target and launch assessments separately; saving a structured native launch requires a supported valid assessment. Unknown launch methods remain visible and unchanged unless edited in Advanced JSON. Strong ETag replacement prevents silent concurrent overwrites. Files uploaded through the browser directory picker are marked non-executable; non-executable files remain eligible as entry points. Artwork cards open the native file picker and upload immediately after selection, with indeterminate progress and result feedback inside the card. An exact retry retains its idempotency key; deletion retains confirmation. ICO is accepted only for Icon and served as normalized PNG. A single Logo card prefers canonical `logo`, displays existing `steam.logo` when canonical artwork is absent, and keeps both bindings when both exist; the older binding remains visible in technical details. A compact custom-role action remains available. Application lists, workspace switcher, overview and Release context use icon thumbnails with initial-letter fallbacks, lazy loading and refresh after replacement. Suggested Steam dimensions are guidance, not constraints. Artwork is App-owned and remains independent of Releases and declaration revisions.

Server Admins can list and create users, change Publish and Server Admin permissions with strong ETags, and revoke another user's personal token. The Users API provides no user-deletion operation. Every signed-in user can inspect, issue, replace, and revoke their own personal token. Its plaintext appears only immediately after issuance and is cleared on dismissal or navigation; direct HTTP has no transport confidentiality. Admins can read redacted diagnostic aggregates, update the dynamic anonymous-read policy with an ETag, and start and inspect online backups. The backup page lists available completed output, exposes the manifest and each member, and can stream-verify member size and SHA-256. Browser downloads do not reliably preserve all portable relative paths, so the Portal offers an explicit per-member export procedure rather than claiming a complete restorable directory. Operators must reconstruct and validate the complete directory offline before restore; restore itself requires the offline CLI and exclusive data-root ownership.

The Portal does not infer release counts, activity feeds, storage history, per-App grants, or global operation lists from incomplete data. Static deployment configuration, user deletion, password recovery, and online restore are unavailable through the current API. New backend capabilities require separate authorization and contract updates.

## Release overview and Artifact Explorer

Release Details surfaces status, Draft publication and Add Artifact actions, supported platforms, Artifacts, launch entry points, installation information when present, and release notes and App description. **Advanced release details** contains version editing for Drafts, declarations, revision history, existing Artifact association, the combined JSON snapshot and deletion. Per-Artifact declarations are under **Advanced association details**. These views retain existing permissions and revision semantics.

Artifact Explorer presents original directories and files with human-readable sizes, hierarchical breadcrumbs, search, downloads and 50-entry cursor pages. Expand a row's technical details to inspect its original path, executable permission and digest. Select a regular file to create or change an association entry point, pick the target platform, and optionally declare NativePortableV1 working directory and literal arguments. Saving validates the point and uses the loaded declaration's strong ETag. An external edit requires reloading before saving again.

## GOG Offline Installer

In Add Artifact select **Import from server storage**, choose **GOG Offline Installer**, open the installer directory in Inbox and choose **Select this directory**. Use **Analyze installer**. If there is more than one setup candidate, choose its executable and repeat analysis. The review distinguishes format and volume evidence, installer UI languages, tagged assets and inferred redistributable groups. Add a game version, product name override, launch candidate or notes if known. Import saves a Draft. Select a launch file to offer a Windows entry point with optional working directory and arguments. Clear the checkbox to retain only the candidate. Open the resulting Release to inspect GOG installation information and publish separately. Older candidate-only manifests support explicit creation from the Artifact Explorer. The Server Storage progress view supports cancellation and retry. [Manifest and limitations](gog-offline-import.md)

## Derived Applications

Choose **Derived** on the application creation form, then create a Draft release. The release details provide an installation recipe editor separate from the Standard App Artifact workflow. Use **Add dependency application** to search by name and see App icons. New dependencies follow the latest publication by default. A dropdown can instead follow a channel or pin a published release.

For each target-platform plan, choose a source Artifact or use the sole Artifact automatically. Choose a named association label to follow it across releases where the label is unique. Browse a Tree Artifact's folders to choose a file or directory, or browse the output paths of a Derived dependency. Enter the destination path relative to the installation root. Reorder copy operations with the arrow actions and choose whether a later file may replace an earlier one at the same path. An individual file can be marked executable.

Preview the final layout, select the launch file from the resulting file picker, and set the working directory and literal arguments. **Save and validate recipe** reports technical issues and shows the resolved component versions for the selected target. **Publish release** freezes the definition after the Server checks all targets again. The Published view displays declared policies, currently selected component versions and the current layout. Moving a channel or publishing another dependency release may change that preview.

The Portal edits recipes through form controls. Advanced JSON authoring and explicit optional dependency-platform allowlists are available through [the API](api.md#derived-apps-and-recipes). The target platform editor and per-target operations cover choosing platform-specific components in the Portal.


**Installation Configuration** is optional on Release Details. Owners and admins can pick associated File or Tree sources, choose destinations and collision policies, configure language and component choices and defaults, order explicitly confirmed prerequisite installers, and select an existing launch point. Preview resolves a concrete platform and selection before saving. Save uses the strong Release declaration ETag and creates a new revision even on a Published Release. Advanced release details retain the raw JSON editor. Existing GOG releases offer an explicit recovered-payload starting point and keep the association's source evidence.
