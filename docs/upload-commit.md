# Reliable upload, commit and recovery

This contract covers bare files, inventory-first bare trees and explicitly imported ZIPs. It does not change [Tree Identity v1](tree-identity.md), publication, authorization or whole-file CAS identity. Upload and registration do not publish a Release. The Server never executes content.

## Session and progress

One stable session identity binds an authorized principal, ingestion mode, immutable target and claims, and one logical finalization operation identity. The bound inputs include the intended App/Release or authorized minimal-creation intent, the file or tree inventory, sizes, hashes and portable attributes. Reuse of an operation identity with different bindings is rejected. Session status and authoritative progress are queryable only by an authorized principal. The operation identity distinguishes retries from a new intentional registration; a fresh operation uses a fresh identity.

The phases are `Receiving → Verifying → Importing` (ZIP only) `→ Committing → Completed`. `Receiving`, `Verifying`, `Importing` and `Committing` may end in `Failed` or `Cancelled` before the registration commit point. Only `Receiving` accepts bytes. The transition to `Verifying` freezes the submitted inventory, target and received bytes. A recoverable storage or process interruption retains or re-enters the safe phase and is not a terminal `Failed` result. Invalid input, conflicting data and unrecoverable integrity failures are terminal `Failed`. Cancellation stops new work, waits for in-flight work to reach a safe boundary, and cleans temporary state; if the durable registration wins the serialized race, the outcome is `Completed` and cancellation cannot undo it. `Completed`, `Failed` and `Cancelled` are terminal for that session. A lost response is resolved by querying its session/operation result, not by creating another operation.

The tree inventory lists every logical path, type, file size, claimed SHA-256 and executable flag required by Tree Identity v1. Validate its structure and limits before accepting bytes; these claims do not prove content. A ZIP session binds the transport ZIP's expected size and SHA-256, has one resumable transport file and no member-level range progress. The ZIP is fully received and verified before import starts.

For each file, validate total size and range bounds. Nonoverlapping ranges may proceed concurrently within resource limits; overlapping writes are serialized against each other. Before accepting a retransmission, compare every intersection with **authoritatively recorded** intervals against the corresponding bytes read from staging; byte-for-byte equality makes that overlap idempotent, and any difference rejects the request without changing accepted progress. Unrecorded bytes from an interrupted write may be overwritten safely. This rule also applies when a response was lost. Acknowledgment follows a successful staging write and a consistent progress-state record in that order; the Server must establish write-before-record ordering and cannot acknowledge memory-only bytes. The record tracks covered intervals and a digest of the staged bytes for each independently revalidatable interval. Range records cannot be treated as an atomic filesystem/SQLite transaction. A crash before acknowledgment may leave staged bytes with no authoritative progress; the client queries and safely retries. An acknowledgment proves receipt only, not full-file SHA-256.

Progress records and staged bytes survive normal process crashes and restarts. No per-range storage-device flush is required. After sudden power loss, reconcile every recorded interval with actual staged bytes and its recorded digest before advertising it as resumed progress; any absent, truncated or mismatching interval is invalidated. The client can query the resulting authoritative intervals and retransmit gaps. Revalidation must read the staged bytes; metadata alone never proves their presence. If staging is not safely isolatable or the record is inconsistent, invalidate the affected file's progress. In-flight writes are quiesced or fenced during recovery. This preserves process-crash durability of acknowledged progress while allowing power-loss rollback of progress.

## Verification and import

Only a complete file enters verification. Independently stream its exact bytes to check size and SHA-256; a supplied hash is a claim. Keep verified staging immutable or otherwise guarded against mutation until CAS promotion. Reject incomplete, conflicting or mismatching content. For a bare tree, validate every inventory entry and compute Tree Identity v1 from verified files and portable attributes. A legitimately reusable, already verified CAS object can satisfy a claimed file without retransmission or another mandatory full hash, provided its durable integrity and references are trusted. Negotiation and responses must be authorization-scoped and must not reveal whether inaccessible private content exists; a hash alone grants neither reuse nor read access.

For explicit ZIP import, verify the complete transport ZIP's received bytes and structure, then parse only supported Store/Deflate members under quotas and path/type rules. Extract into isolated staging with bounded resources, verify each extracted file, and build the canonical logical tree under [Tree Identity v1](tree-identity.md). The temporary ZIP is never registered as an additional Artifact. A crash before registration discards or reconciles incomplete extraction and restarts import from a still complete, verified ZIP; decompression checkpoints are unnecessary. If power loss damages or removes that ZIP, invalidate its ranges for retransmission or fail the session safely.

## CAS and catalog commit

SQLite is the logical registration authority; filesystem CAS writes are separate. A recoverable, persistent prepared-operation claim protects each required CAS identity against garbage collection before promotion or reuse. Acquisition and garbage-collection decisions are serialized against each other. Promotion uses only immutable verified bytes. An existing object is reused only when its identity and trusted verified state match; never overwrite it. Concurrent installers of the same digest elect one object and discard the other verified candidate. Partial files have temporary names and are never treated as CAS objects.

For a new object, put a complete verified candidate on the destination CAS filesystem. If staging is on another filesystem, copy into such a temporary candidate; cross-filesystem rename is not assumed. Synchronize the candidate's content and required file metadata, atomically install it without overwriting an existing object, and persist the affected directory entries (including newly created parent directories). A rename alone is not a power-loss durability barrier. If the filesystem cannot provide the required atomic install and durable file/directory semantics, finalization must fail rather than report `Completed`. Interrupted candidates are reconciled or deleted; an installed object without a catalog reference remains protected by its recoverable operation claim until recovery resolves it.

Only after **all** required CAS objects are durable may one durable SQLite transaction register the Artifact identity, CAS references, Release–Artifact association, any authorized implicit App/Release creation, operation identity and result, terminal `Completed` state, and outstanding temporary-cleanup obligation. It must validate the target still permits the association, including immutable Published Release composition, under the same serialization that prevents conflicting catalog changes. No partial Artifact is visible before that transaction. Configure SQLite journaling and synchronization so a successful commit is power-loss durable on the supported storage; SQLite does not flush unrelated CAS files. Return `Completed` only after the transaction's durable commit. The result remains queryable and repeated finalization returns it without creating another App, Release or association. Authorization and visibility remain independent of content identity.

The guarantees assume a filesystem, SQLite configuration and storage device that honor successful synchronization and write-ordering operations. They do not cover broken flush semantics, unrecoverable media failure or independent corruption. A successful SQLite transaction before durable CAS is insufficient.

## Recovery, cleanup and concurrency

On restart, fence old workers, read persistent session/operation state and reconcile staging, prepared claims, CAS objects and catalog records before making affected operations available. `Receiving` revalidates progress; `Verifying` rechecks or safely restarts verification; `Importing` restarts from a valid ZIP; `Committing` first reads the authoritative SQLite outcome. If its transaction committed, return the stored `Completed` result and continue cleanup. If it did not, verify durable CAS objects and claims, then retry or safely fail. Never infer commit success from a CAS file or retry side effects blindly. Recovery and cleanup are idempotent. A failed precommit operation exposes no Artifact and releases its claims after reconciling candidates.

The session and committed result remain discoverable for the lifetime of the registration. If that registration is later permanently deleted, the old session cannot be reused to recreate it; an authorized new registration requires a new operation. Terminal results may be retired only with their registration and with safe rejection of old session/operation identities. An uncertain SQLite outcome is resolved from persistent state. Concurrent finalizers for one operation serialize to one authoritative result; different bound inputs under one operation identity are rejected.

Sessions expire after a configurable idle period. Active authorized transfer, verification, import or commit work holds a recoverable lease or equivalent fence, so expiry cannot race it. Cancellation/expiry removes only that operation's unneeded temporary bytes and claims; it never deletes referenced or otherwise protected CAS objects. Completed may be returned with a durably recorded, pending post-commit cleanup obligation. ZIP transport and import staging are removed asynchronously; cleanup failures remain visible to operators and retry automatically until resolved. Upload-temp cleanup is distinct from permanent App/Release deletion, whose success still waits for all mandatory managed-state and storage cleanup.

Whole-file CAS objects may be shared. Registration, reuse, deletion and garbage collection coordinate through catalog references **and** recoverable prepared-operation protection. Garbage collection rechecks both under the same synchronization used to acquire protection before unlinking, and persists removal as needed; it cannot remove an object needed by an active or recoverable commit. Recovery eventually releases abandoned claims and reclaims unreferenced objects and partial candidates. Physical CAS ownership is internal; possession of a digest does not grant authorization.

Large sequential writes, bounded buffering, adaptive concurrency, efficient many-file handling, grouped progress persistence where acknowledgment ordering remains correct, verified-object reuse and few redundant reads/copies are permitted. Final durability barriers remain mandatory; per-range physical `fsync`, zero-copy, universal single-pass hashing and fixed throughput are not promised.

## Conformance scenarios

The observable result in each case follows the invariants above. `Completed` always means both CAS and catalog are power-loss durable; progress acknowledgments have the weaker guarantee.

| # | Interruption or race | Required observable behavior and invariant |
| --- | --- | --- |
| 1 | Network disconnect during receipt | Session and authoritative covered ranges remain queryable; missing ranges can be sent again. No Artifact is registered. |
| 2 | Process crash before range acknowledgment | Unacknowledged range may be absent from progress; retry is safe after the progress query. |
| 3 | Process crash after range acknowledgment | Acknowledged range remains in resumed progress after normal restart; staging bytes and record agree. |
| 4 | Power loss after acknowledgment, before finalization | Missing/mismatching staged ranges are invalidated and retransmittable; no metadata-only progress is trusted. |
| 5 | Identical range retransmission | Staged bytes compare equal; progress and content remain unchanged, retry succeeds idempotently. |
| 6 | Conflicting range retransmission | Different overlap is rejected without modifying acknowledged bytes or progress. |
| 7 | Concurrent overlapping ranges | Writes are serialized; the overlap has one byte value, and conflict is rejected. |
| 8 | Full-file hash mismatch | No registration; session becomes terminal `Failed` for unrecoverable supplied-content mismatch. |
| 9 | Crash during ZIP import | Valid complete ZIP is retained; partial extraction is reconciled/discarded and import restarts. |
| 10 | Crash during CAS promotion | Partial candidate is never visible as CAS; recovery verifies an installed object or retries from verified staging. |
| 11 | Failure before SQLite commit | No Artifact or association is visible; prepared objects remain recoverable, then retry or cleanup. |
| 12 | Uncertain SQLite commit | Recovery reads authoritative operation/result state; it returns the committed result or safely resumes without duplicate side effects. |
| 13 | Crash after commit, before response | Query/retry returns the same `Completed` result; no second Release or association appears. |
| 14 | Crash during asynchronous ZIP cleanup | `Completed` stays valid; pending obligation resumes and removes temporary ZIP without touching registered CAS. |
| 15 | Duplicate finalization | Same bound operation returns one stored result; different binding is rejected. |
| 16 | Concurrent finalization | One winner commits; other caller observes the same result or the same terminal failure. |
| 17 | CAS reuse concurrent with deletion | Prepared claim and reference/GC serialization protect a needed object; deletion cannot unlink it until safe. |
| 18 | Session expiry during active transfer | Active fenced work prevents expiry; after it becomes idle and expires, cleanup is safe and observable. |
| 19 | Reuse of verified CAS object | Authorized reuse may skip transfer/rehash; no unauthorized existence signal or content access is exposed. |
| 20 | Power loss immediately after `Completed` | Registration, result, references and required CAS bytes survive; cleanup may resume afterward. |
