# Deployment and operations contract

This contract governs the single-node MVP. [Architecture](architecture.md), [API v1](api.md), [Tree Identity v1](tree-identity.md) and [reliable upload and commit](upload-commit.md) retain their identity, authorization and durability guarantees.

## Container, storage and lifecycle

One OCI container runs the API, Web UI and background workers. Official images target `linux/amd64` and `linux/arm64`. Docker Compose is the reference deployment; a TrueNAS SCALE Custom App can supply the same image, configuration and persistent volume without a TrueNAS-specific Server dependency. No external database, broker or orchestrator is required. One persistent root data volume logically separates SQLite, CAS, upload staging, backups and operational state. Both bind mounts and Docker named volumes are supported. A single root mount does not prove that its subdirectories share a filesystem: the Server checks actual mount boundaries and uses the F2.2 cross-filesystem promotion path where needed.

The container runs under a configurable non-root UID/GID. The operator provisions volume ownership and permissions in advance; startup neither requires root nor recursively changes ownership. The process needs read/write/create/delete and directory synchronization on the relevant managed locations, reliable filesystem locking for SQLite, and the atomic install plus file and directory durability properties required by F2.2. SQLite on NFS or SMB is unsupported. Startup refuses demonstrably incompatible mounts, locking, permissions or durability operations, with a safe diagnostic. A successful probe does not certify hardware flush behavior; unprovable properties are documented assumptions. No host filesystem brand is mandatory.

A bounded graceful shutdown stops new work, fences uploads and workers, completes or records in-flight durable transitions, and closes SQLite safely. If the timeout expires, restart reconciliation handles interrupted phases; an acknowledged range retains only its F2.2 process-crash guarantee. Persistent-volume restart is ordinary F2.2 recovery, not backup restore. Only one Server or offline maintenance process may own a data root at a time.

## Configuration, bootstrap and transport security

Configuration precedence, from lowest to highest, is built-in defaults, configuration file, and explicitly documented environment overrides. This precedence applies to deployment configuration; dynamic catalog settings persisted in SQLite are not reset by startup defaults. Secret values come from separate secret sources; protected secret files are preferred. Supplying both file and environment sources for one secret is a configuration error. Environment secrets are allowed but may be exposed by container inspection or process environments. Invalid, unknown security-critical or conflicting settings fail startup; effective non-secret settings and their source may be diagnosed, never secret values. Documented dynamic settings, including catalog policy and safe resource limits, take effect through their API/configuration contract; storage layout, UID/GID, database mode, listener, proxy trust, secret-source changes and migration-related settings require a controlled restart. A change cannot bypass existing authorization or durability rules.

An initial Server Admin is created only on an uninitialized data root from a one-time bootstrap secret supplied through protected configuration. Bootstrap is idempotent, consumes or invalidates that secret after first successful initialization, never resets existing accounts, and never runs on a restored database. Missing or unsafe bootstrap input blocks first initialization. Password hashes and personal-token verifiers remain in the database; plaintext credentials and tokens do not. External verifier/pepper secrets, if configured, are restore prerequisites; missing required values prevent activation. Restored password hashes and personal-token verifiers remain usable with those secrets. Browser-session signing secrets are external; if changed, existing browser sessions are invalid and users log in again.

The application serves HTTP. A trusted external reverse proxy terminates TLS for secure remote access; direct LAN HTTP is supported without confidentiality. Non-localhost browser login requires a secure origin for the mandatory `Secure` session cookie; direct HTTP remains usable for API clients that accept its transport risk. Only explicitly configured trusted proxy peers may supply forwarded protocol, host or client-address headers; untrusted headers are ignored. The proxy must preserve request bodies, `Content-Range`, Range, Host/Origin and secure-cookie semantics, and restrict access to administrative and backup traffic. Bearer tokens, `Secure`/`HttpOnly`/`SameSite=Lax` browser cookies, Origin checks and CSRF protection follow [API v1](api.md). Built-in certificate management and OAuth/OIDC are not required.

## Online backup and portable representation

A Server Admin starts an online backup with `POST /api/v1/backups` and an `Idempotency-Key`; an external scheduler may call that API. There is no required internal scheduler. The operation uses existing `Accepted`, `Running`, `Completed`, `Failed` and `/operations/{id}` semantics. Only `Completed` backups with verified available output appear in `/backups`. A portable backup is a directory with a versioned `manifest.json`, one consistent SQLite snapshot, all CAS files required by that snapshot, and durable recovery/cleanup metadata needed to resume its logical state. The format version is `1`. The manifest has exactly one `SqliteSnapshot` member at `catalog.sqlite`; each `CasObject` member is at `cas/<64 lowercase SHA-256 hex>`. Durable recovery and cleanup metadata is in the SQLite snapshot. A CAS member path digest must equal that member’s recorded SHA-256. Member IDs are opaque and unique; relative paths are unique and contain no traversal, byte sizes and SHA-256 digests are recorded, and paths cannot escape the backup directory. The format has no Docker, TrueNAS, CPU or absolute-host-path dependency and is restorable on a compatible Linux host across amd64/arm64. No single compressed archive is required.

The backup boundary is one SQLite read-consistent catalog state at a defined commit point. Before releasing protection against concurrent GC/deletion, the Server establishes durable backup pins for the exact CAS set required by completed registrations and durable recovery/cleanup obligations retained in that state. Uncommitted upload and commit claims are retained for safe invalidation on restore, but do not require absent staging or unpromoted candidates in the backup. Pin acquisition and GC/deletion decisions serialize; new commits after the boundary are excluded. The SQLite snapshot captures the boundary state, including users, declarations, completed registration/idempotency results, and durable deletion, commit and cleanup obligations. The Server copies each pinned CAS object and verifies its SHA-256 and size. Upload staging bytes, temporary ZIPs and prior managed backup output are excluded, preventing recursive copies. Backup-specific inventory and pins are source-instance local. Restore preserves each historical backup operation ID, idempotency binding, terminal status and `backupId`; it verifies independently present local output against the manifest and every member before setting `backupOutputAvailable: true`. Missing, incomplete or corrupt output yields `backupOutputAvailable: false` while historical `Completed` remains `Completed`. Only completed operations with verified available output appear in `/backups` or permit manifest/member downloads; direct requests for unavailable output return `404 not_found`. Stale backup pins are released after reconciliation; registration idempotency and deletion obligations are untouched. An exact authorized `POST /backups` replay returns `202` with the same historical operation ID and current availability flag; the historical operation and key binding remain for the lifetime of the restored catalog, so the key cannot start a replacement backup. The Server durably writes and verifies all members, then durably finalizes the manifest as the validity marker, and durably records `Completed`; only then can it release pins. A crash before that point leaves an invalid temporary backup that recovery resumes safely or removes, and reconciles its pins. A completed backup is independently restorable under the documented filesystem/storage flush assumptions; copying a live SQLite file followed by CAS files does not meet this contract.

The backup contains password hashes and stored personal-token verifiers, not plaintext passwords or tokens. It excludes bootstrap secrets, external TLS keys, reverse-proxy configuration, host secret files and other external deployment credentials. It is sensitive and must be protected as credential-bearing data. Only Server Admin can list backups, read a completed manifest or download a member through opaque IDs; the manifest and member API expose portable relative paths, not host or CAS paths. The operator can reconstruct the directory from `GET /backups/{id}` and `GET /backups/{id}/entries/{entry_id}` and validate it offline. A failed or incomplete backup is not advertised as available.

## Offline restore, corruption and migration

Restore uses `app-depot-server restore --backup-dir <directory> --data-root <directory> [--replace]` inside the stopped container or an equivalent one-off container with the same volume. `--replace` is required for a nonempty, fully stopped target. Exit code zero means validated activation completed; any failure is nonzero. It requires exclusive data-root ownership and is never exposed through HTTP. It targets an empty instance or a fully stopped instance under an explicit replacement procedure. The CLI accepts a backup directory and destination data root, checks format/version and target-image compatibility, validates manifest paths, member sizes and SHA-256, SQLite integrity and required CAS identities, and prepares isolated destination state without overwriting a live instance. It activates the validated state atomically where supported; otherwise it uses a recoverable activation marker and refuses service until completion or rollback to the prior stopped state. A failed validation leaves the destination unavailable and the prior stopped state untouched. Restore succeeds only after activation and required validation; startup then performs mandatory recovery before readiness.

Because staging is excluded, restore atomically marks every incomplete Upload Session `Cancelled` with `cancellationReason: RestoreInvalidated`, preserves its session/operation IDs and original creation-key binding, invalidates all range claims and releases unneeded pins. The bound finalization operation becomes `Failed` with `session_cancelled` and the same reason; no Completed registration is invented. It never resumes such a session; a new upload requires a fresh key and operation identity. An exact authorized `POST /uploads` retry of the old creation key returns `201` with the same cancelled session, never a new one. Authorized status/result reads expose `Cancelled` and `RestoreInvalidated`; progress, range writes, inventory changes and finalization return `410 session_cancelled` with that reason. The historical session, cancellation result and creation-key binding remain authorized and queryable for at least 24 hours after restore unless their target is permanently deleted earlier; ordinary terminal-session retirement may follow. Permanent deletion of their target removes dependent session records under the existing strict cleanup contract. After retirement or deletion, a persistent metadata-minimal key tombstone rejects the old key with `409 idempotency_conflict`; it never creates a new session or reveals deleted content. Session and operation IDs are never recycled. Ordinary process restart with the original volume still follows F2.2 resumption. Completed registrations and their saved idempotent results remain valid. Durable deletion/access-revocation and cleanup obligations in the snapshot remain effective and resume; no interrupted operation is falsely marked `Completed`. Restored authentication follows the captured database state and the separately reconfigured external secrets. Restoring an older backup can reintroduce resources deleted after its boundary; events after the boundary are not preserved. Resources already revoked within the backup remain revoked.

Known-corrupt CAS bytes are never served as valid; affected content fails closed and diagnostics identify the affected logical operation without leaking private metadata. SQLite integrity failure prevents readiness and catalog service; the Server does not invent registrations, drop records or discard cleanup obligations to start. Corruption recovery requires an explicit operator procedure: isolate the instance, inspect structured stdout/stderr logs, run `app-depot-server diagnose --data-root <directory>` with exclusive offline ownership, restore a verified backup or repair under exclusive ownership, validate again, then resume. The offline diagnostic command is read-only, reads what remains accessible, reports safe structured status and a nonzero exit code for detected failure, and does not require working HTTP, SQLite-backed Admin authentication or successful catalog reads. It redacts credentials, secrets and private metadata. Normal protected HTTP diagnostics remain available only when authentication works; there is no public emergency authentication bypass. Process recovery, power-loss reconciliation, corruption recovery and offline restore are distinct procedures.

Persistent schema and data formats are versioned. Before an upgrade the operator stops the Server, verifies image/data compatibility and a restorable pre-upgrade backup, and runs preflight checks. Exclusive migrations preserve F2.2 commit/recovery guarantees, validate their result, and allow serving only after mandatory recovery. A failed migration leaves the new version NotReady and requires recovery from the verified backup; an irreversible migration is not automatically rolled back. Incompatible downgrade is refused. Returning to an older image alone does not restore older data.

## Health, logs and diagnostics

`GET /api/v1/health/live` reports process responsiveness, including during recovery; `GET /api/v1/health/ready` returns `200` only after mandatory storage validation, migration and recovery permit safe requests, otherwise `503`. Both are minimal unauthenticated responses with no private data. Startup, mandatory recovery and migration are NotReady; a full rehash of every CAS object is not required at startup. Noncritical cleanup may continue after Ready if access and integrity remain safe. Degraded affected content fails closed; a catalog-wide integrity failure is NotReady. Shutdown becomes NotReady before stopping.

Structured JSON logs go to stdout/stderr with request and operation IDs, severity and safe event codes. Logs exclude credentials, tokens, sensitive headers, unnecessary private metadata and raw CAS paths. Server Admin `GET /api/v1/admin/diagnostics` returns redacted health, recovery/migration state, storage pressure, request error/latency aggregates over a reported measurement window, active upload/transfer counts, pending/retryable cleanup counts and backup status counts. It is not a content listing, configuration dump or raw log endpoint. Metrics require no Prometheus or OpenTelemetry stack. Admin responses and backup downloads require protected transport and authorization.

## Operational conformance scenarios

| # | Situation | Required outcome |
| --- | --- | --- |
| 1 | First startup with protected bootstrap secret | One Admin is created once; readiness waits for initialization. |
| 2 | Restart initialized volume | No account reset; F2.2 recovery runs before readiness. |
| 3 | Readiness during recovery | Live may be `200`; ready is `503` until mandatory reconciliation finishes. |
| 4 | Shutdown during upload | New work stops; restart resumes only authoritatively acknowledged progress. |
| 5 | Backup with concurrent upload | Boundary excludes later registration; staging is absent; completed registrations at boundary remain valid. |
| 6 | Backup with concurrent CAS GC | Durable pins protect its exact CAS set until verified completion. |
| 7 | Interrupted backup | No valid manifest is advertised; recovery reconciles temporary output and pins. |
| 8 | Restore on compatible other host/CPU | Portable paths and verified state activate; prior backup operations retain `Completed` while missing output is unavailable. |
| 9 | Restore without staging | Incomplete uploads become `Cancelled`/`RestoreInvalidated`; old keys cannot recreate them; Completed results survive. |
| 10 | Restore during deletion | Revoked access remains revoked; cleanup obligation resumes. |
| 11 | Corrupt CAS object | Affected bytes are not served; diagnostics and explicit recovery are required. |
| 12 | SQLite integrity failure | Catalog is NotReady; logs and offline diagnostics work without database-backed HTTP authentication. |
| 13 | Compatible migration | Verified backup and exclusive migration precede Ready. |
| 14 | Failed migration | New image stays NotReady; recover from pre-upgrade backup. |
| 15 | Incompatible downgrade | Startup refuses it; older image alone cannot roll back data. |
| 16 | Unsafe filesystem/mount | Demonstrable incompatibility rejects startup; unprovable flush behavior remains an assumption. |
| 17 | Non-root permission failure | Startup reports failure without root escalation or recursive chown. |
| 18 | Diagnostics and secret redaction | Non-Admin cannot read diagnostics/backups; Admin sees aggregates, never secrets or private bytes. |
